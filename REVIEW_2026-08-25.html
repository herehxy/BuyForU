4. 新发现问题

P2 heartbeat 90 秒硬阈值与 PLANNING 命令期限（210s）不一致

位置：CommandWorker.java 91–105（heartbeat）与 237–239（shouldRenewLease）；期限定义见 CommandService.java 52–56（PLANNING 210s / TRANSACTION 50s / CONTROL 15s）。

行为：心跳每 10 秒检查一次：staleBefore = now - 90s，而 shouldRenewLease 用命令首次开始时间（started_at 在首次 claim 时写入，COALESCE(started_at, now())）判断——命令从开始算超过 90 秒，即使仍在正常执行（DeepSeek 规划、多次重规划），也会被 inFlight.cancel + worker.interrupt() 强制中断。

影响：PLANNING 命令允许 210 秒，但 90 秒即被中断。TRANSACTION（50s）、CONTROL（15s）不受影响。慢模型或三级 Replan 场景下，规划命令会在 90–210 秒窗口内被误杀；中断后命令进入失败/恢复路径（attempts 递增），极端情况在 3 次尝试后 EXPIRED，而本可成功的规划无法完成。

证据：CommandWorkerTest 仅固定了"startedAt 早于 90s 返回 false"的单测，未覆盖"90–210s 合法规划窗口"。

建议：卡住判定不应使用首次开始时间，应改为①命令期限 deadlineAt（到期才停止续租并取消），或②lease 最后心跳时间（与 recoverExpired 的陈旧语义对齐）；90 秒硬编码改为配置项。需要补充"运行超过 90 秒仍在进展的命令不被中断"的集成测试。

P3 观察项

  • 用户锁 TTL 240s 无心跳续期（RedisFairQueue.tryAcquireUser）：注释明确"崩溃后最多堵 240 秒"。命令期限（≤210s）均小于 TTL，正常路径安全；仅当 recoverExpired 后 releaseUser 因 Redis 短暂故障失败时，该用户会被堵至 TTL 自然过期。属已知边界，建议在指标中暴露该等待时长以便观测。
  • MCP 写调用超时 5s / 重试 2 次（SpringMcpCommerceToolClient.call）：Commerce 下单事务若超过 5 秒，Agent 侧会超时重试——安全性由 effect 幂等兜底（同 effectId 重放返回原结果），正确性无问题；长尾延迟场景可评估是否将写超时放宽到命令期限（50s）内与事务上限对齐。
  • CONTROL lane 在 Redis 故障时放行（RedisAdmissionController.admit）：有意设计（取消/拒绝必须可用），与"写路径 fail-closed"并存是合理的分级降级。
  • 队列重建（reconcileRedisIndex）：已确认只取 QUEUED/RETRY_WAIT，不会把已完成命令重新入队，无风险。

5. 架构与工程优点

  • 交易事实与 LLM 严格隔离：LLM 只生成 PlanSpec，LangGraph4j 固定图执行；Commerce 经纯 Java 端口 + MCP 仅作 Adapter，防止模型污染交易边界。
  • 幂等是系统性设计而非补丁：命令级（idempotency_key + requestHash + 唯一索引）、Effect 级（effect ledger + advisory lock）、资源级（source_snapshot_id 唯一）三层幂等，覆盖网络超时、进程崩溃、并发重放全部窗口。
  • fencing 完整：epoch + stateVersion + lease_owner 条件更新，旧 Worker 的写回被栅栏拒绝并显式标记 STALE_EXECUTION。
  • 故障分级降级：Redis 协调层 fail-closed（写）/ 放行（读与 CONTROL），CircuitBreaker 保护协调依赖；错误分类沿 cause chain，对外固定公开文案，不泄漏 MCP 细节。
  • 热路径局部化：下单只回收当前 SKU 过期预占（避免全表锁），后台批量回收用 SKIP LOCKED；搜索批量加载促销规则消除 N+1。
  • 测试即文档：每个测试类顶部注明验证的风险点，故障注入位置说明崩溃窗口；测试命名与不变量一一对应。
