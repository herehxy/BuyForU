4. 新发现问题

P2 heartbeat 90 秒硬阈值缺陷仍未修复，且已被测试固化

位置：CommandWorker.java:91（阈值）与 237–239（shouldRenewLease）；期限定义见 CommandService.java:52–56。

矛盾事实：

CommandService.java:52-56   PLANNING 期限 = 210s / TRANSACTION = 50s / CONTROL = 15s
CommandWorker.java:91       Instant staleBefore = Instant.now().minusSeconds(90);   // 硬编码
CommandWorker.java:237      shouldRenewLease(startedAt, staleBefore)                // 用首次开始时间判定

影响：PLANNING 命令允许 210 秒，但运行满 90 秒即被 inFlight.cancel + worker.interrupt() 强制中断。慢模型响应或三级 Replan 场景下，本可成功的规划会在 90–210 秒窗口内被误杀，重试 3 次后进入 EXPIRED。TRANSACTION（50s）与 CONTROL（15s）不受影响。

本次新增的关键判断：CommandWorkerTest.staleOrMissingStartTimeControlsLeaseRenewal 中的断言 assertFalse(shouldRenewLease(startedAt 早于阈值 30s, staleBefore)) 已将"按首次开始时间判定"这一错误语义固化为预期行为。这意味着该缺陷从"未被测试发现"升级为"被测试保护"——任何修复都必须同步修改此测试，否则会立即失败。这是本次审查中最需要注意的一点。

建议修复：① 卡住判定改用命令期限 deadlineAt（到期才停止续租），或改用 lease 最后心跳时间（与 recoverExpired 的陈旧语义对齐）；② 将 90 秒阈值配置化；③ 同步修正 CommandWorkerTest 的断言，并补充"运行 90–210 秒仍在正常进展的命令不被中断"的用例。

P3 违反项目自身声明的规范：魔法数字散落

ConcurrencyProperties.java 类注释明确承诺："所有容量参数均可通过环境变量调整，代码中不散落不可运维的魔法数字。"

而 CommandWorker.java:91 的 minusSeconds(90) 正是一个散落在代码中的魔法数字，且未纳入 ConcurrencyProperties。这使该参数无法运维调整，也是 P2 长期未被发现的直接原因——期限常量集中在 CommandService，而中断阈值孤立在 CommandWorker，两者无任何引用关系可供校验。

建议：新增 staleCommandThreshold 配置项，并让 CommandWorker 与 CommandService 的期限常量共享同一配置源。
