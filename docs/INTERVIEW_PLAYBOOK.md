## 0. 怎么用这份文档

面试前按这个顺序过一遍：

1. 先背 §1 事实卡。**说不准的数字比说不出更致命**——面试官会顺着一个错数字往下挖。
2. 再练 §2 的三档口述。30 秒版本决定面试官想不想听两分钟版本。
3. §3 挑 2–3 个技术点深挖到能画图、能写 SQL、能说清"去掉它会怎样"。**不要五个都讲一半。**
4. §4 是追问链。真实的面试是"你说 A → 他问 A 的边界 → 你答 → 他问再深一层"。提前把链条走通。
5. §5 是翻车点，§6 是踩坑（这部分最能体现你在做工程），§7 是诚实边界。

一个总原则：**每个技术论断都要能接上"我怎么证明它"**。面试里"我做了三层幂等"是 0 分答案，"三层幂等分别是入口/领域/恢复，领域层用 effect ledger 加 advisory lock，我用 XX 用例证明去掉它就会变红"才是满分答案。

## 2. 三档口述口径

### 30 秒版（决定面试官要不要往下听）

> "BuyForU 是一个电商购物 Agent。用户用自然语言说要买什么，模型只负责生成一份**受约束的 `PlanSpec`**，真正的执行走一张**固定的 LangGraph 状态图**——模型不能决定状态怎么迁移。交易侧是独立的服务，通过 MCP 暴露 11 个工具，Agent 这一侧**没有任何事务能力**，一致性全部落在交易服务的事务里。
>
> 我主要解决的是：长链路 + 人工等待场景下，**任何中断重试都不能重复扣库存、不能重复下单**。手段是三层幂等、行锁加 CHECK 约束防超卖、以及 effect ledger。"

**要点：** 先说"模型不管状态迁移"这个反直觉的设计，面试官一定会追问。

### 2 分钟版

> "项目分四个模块。`commerce-port` 是契约，`commerce-service` 是交易域，`agent-app` 是编排，`web` 是前端。
>
> 请求进来先被 Redis 令牌桶按用户限流，然后落成一条**可恢复的异步命令**——因为 LLM 调用是几十秒级的，不能占着 HTTP 连接。这条命令由 Worker 短租约领取执行，租约 30 秒、每 10 秒心跳续租。执行会推进 LangGraph 状态图，图是固定的 12 个节点，中间有三个停靠点等人工审批。
>
> 交易一致性上，我把它拆成三层幂等：**入口层**用 `Idempotency-Key` 加唯一索引，并发冲突时把数据库唯一约束当作并发信号重查重放；**领域层**是 effect ledger，用 `advisory lock` 串行化同一幂等键，用 `requestHash` 防止同一把键被拿去做别的业务；**恢复层**是 `orders.source_snapshot_id` 唯一，即使客户端换了新的网络幂等键，同一个快照也只能生成一个订单。
>
> 防超卖不是靠应用层判断，而是 `inventory.available_quantity` 上的行锁加 `CHECK (available_quantity >= 0)`——**数据库是最终裁判**。
>
> 另外我把 `order_cancel` 作为第二条写路径补上了，因为只有一条写路径时，故障演练只能验证'同一操作的重放'，验证不了'两个写路径交叉争抢同一资源'。"

### 5 分钟版

在 2 分钟版基础上补三块（按面试官兴趣挑）：

1. **崩溃恢复的三层状态分工**：LangGraph checkpoint 负责"图走到哪"，`agent_run` 负责"业务上是什么状态"，`effect_record` 负责"副作用做过没有"。**状态能重放，副作用不能重做**，这三件事必须分开存。
2. **慢调用不拖垮数据库**：网络等待期间不持有数据库连接。租约领取是短事务，提交即归还连接；MCP/LLM 调用全在事务外；Outbox 也是"短事务标 CLAIMED → 提交 → 事务外发 HTTP"。
3. **执行栅栏**：每个 run 有一个单调递增的 `execution_epoch`，旧 Worker 的所有写回都带 `WHERE execution_epoch = ?`，被接管后就写不进去了。

## 3. 五个硬核技术点（原理 + 代码锚点 + 证据）

### 3.1 三层幂等

**为什么需要三层，而不是一层？** 因为每一层挡的失败模式不一样：

| 层 | 机制 | 挡住的失败模式 | 代码锚点 |
| --- | --- | --- | --- |
| 入口 | `Idempotency-Key` + 唯一索引 | 用户连点、客户端重试、网络重发 | `CommandService.accept` |
| 领域 | effect ledger + advisory lock + `requestHash` | 同一请求被不同调用路径重复执行 | `JdbcCommerceEngine.beginEffect` |
| 恢复 | `orders.source_snapshot_id` UNIQUE | **客户端换了新的幂等键**、响应丢失后重建请求 | `JdbcCommerceEngine.createOrder` |

第三层是最容易被忽略的一层：前两层都假设"请求身份是稳定的"。如果客户端每次重试都生成一个新的 `Idempotency-Key`（很多 HTTP 客户端库的默认行为），前两层全部失效——只有"来源快照唯一"这条能兜住。

**领域层的四道机关：**

| 机关 | 挡住什么 |
| --- | --- |
| `pg_advisory_xact_lock(hashtextextended(key, 0))` | 同一幂等键的并发进入（**先排队，而不是靠后面撞行锁**） |
| `SELECT ... FOR UPDATE` | 读到别的实例正在写的、未提交的记录 |
| `requestHash` 校验 | **同一把键被拿去做不同的业务请求**（否则会稀里糊涂重放错误结果） |
| 三态判定 | `COMPLETED` → 重放结果；`PENDING` → `EFFECT_IN_PROGRESS`；无记录 → 插入 |

**入口层里最值得讲的一行**：并发下唯一索引冲突时，**不要抛错，要重查后重放**。数据库的唯一约束是最终裁判，`DataIntegrityViolationException` 是并发信号而不是错误。少了这个 catch，两个并发请求里仍然会有一条失败。

**会被追问：** "`pg_advisory_xact_lock` 和 `SELECT FOR UPDATE` 不是重复了吗？"
答：不重复。advisory lock 按**幂等键**排队，粒度是逻辑键；`FOR UPDATE` 锁的是**已存在的那一行**。没有记录时没有行可锁，所以必须靠 advisory lock 先串行化——否则两个并发请求都会看到"无记录"，然后都去 INSERT，其中一个撞唯一索引。advisory lock 是事务级的，提交或回滚时自动释放，生命周期和整个事务对齐。

### 3.2 防超卖：数据库是最终裁判

```sql
-- V1__commerce_core.sql
available_quantity INTEGER NOT NULL CHECK (available_quantity >= 0)
```

**关键判断：不要用应用层的 `if (stock >= qty)` 来防超卖。** 那个判断在并发下必然失效（读-改-写不是原子的），而且一旦失效就是**负库存**这种静默数据损坏。

真正的机制是：

1. `SELECT ... FOR UPDATE` 锁住 `inventory` 行；
2. 在锁内做条件扣减，**用受影响行数判断是否成功**；
3. `CHECK (available_quantity >= 0)` 作为最后一道兜底——**即使应用层逻辑被改错，数据库也不会让库存变成负数**。

**库存守恒不变量（订单取消引入的最强断言）：**

```
可售数量 + ACTIVE 未过期预占 + 非取消订单的 CONSUMED 预占 == 初始总量
```

这条断言的价值我用实验量化过：把订单取消的回补数量写死成 `+1`，三条集成测试变红，而"库存恰好 +1"那条单点断言**保持全绿**——因为那一单的数量本来就是 1。**单点断言对"回补金额算错"完全失明，守恒律抓住了它。**（`ORDER_CANCELLATION_DESIGN.md` §11.7 实验 6）

### 3.3 订单取消：两道栅栏是纵深防御，不是重复

这是我主动补的第二条写路径。理由不是"多一个功能"，而是**只有一条写路径时，"事务一致性 + 并发治理"这条主线无法被证明**——单路径下故障演练只能验证"同一操作的重放"。

补上取消之后，状态机第一次出现**吸收态**（`CANCELLED` 不可逆）、第一次出现**逆向操作**（回补库存）、并且第一次可以断言**跨聚合的全局不变量**。

**事务内四步：**

```
① advisory lock 排队 + effect ledger（命中 COMPLETED 直接重放，零副作用）
② 栅栏①  订单维度  UPDATE orders … WHERE status='PENDING_PAYMENT'
③ 栅栏②  预占维度  UPDATE inventory_reservation … WHERE status='CONSUMED'
④ 回补库存 + 写 Outbox（同一事务提交）
```

**两道栅栏守的是两个不同维度：**

| 机制 | 守什么 | 挡住的场景 |
| --- | --- | --- |
| effect ledger | 同一个**请求**只执行一次 | 连点、重试、重放 |
| 栅栏① 订单 | 同一个**订单**只能被取消一次 | 幂等键因任何原因算错、换了个键再来 |
| 栅栏② 预占 | 同一笔**库存**只能被归还一次 | 预占状态被外部破坏、订单与预占不匹配 |

**纵深防御不是修辞，我实测过**：去掉栅栏①，6 条集成测试变红，但红的形态是**栅栏② 抛出 `RESERVATION_STATE_INCONSISTENT`**——第二道防线真的接住了，没有退化成静默的数据损坏。

**幂等键为什么锚在 `(userId, orderId)` 而不是 `runId`？**（这是一个只答得出对的、答不出就说明没真做过的问题）

- **订单不记录产生它的 Run。** 取消多半从订单页发起，那时 Run 早结束了，服务端根本没有 `runId` 可用。
- **就算硬加上也会坏。** 用户在两个会话里各点一次，同一订单经两个 Run 取消会派生出**两个幂等键**，ledger 挡不住，库存被**静默回补两次**——这是数据损坏，不是报错。
- **也不接收客户端传来的键。** 客户端能伪造重试就能伪造双重回补。幂等身份由服务端从 `(userId, orderId)` 确定性推导。

派生规则被**字面量哈希锁**钉死：`user-1` / `order-1` 必须产出 `b709d264d70a6440ceeebf0620b296f0644149ad69fa712437f2dfe121641bfd`。

**另一个刻意的取舍：** 新增 `RELEASED_BY_CANCEL` 而不复用 `RELEASED`。`RELEASED` 是"未成交就释放"（用户放弃、预占到期回收），`RELEASED_BY_CANCEL` 是"成交后撤销并回补"——两者对账口径和指标含义完全不同，混用之后事后就无法回答"这批库存是被用户退回还是被租约回收的"。

**锁顺序是约定，不是编译器保证：**

```
orders → inventory_reservation → inventory
```

`createOrder` 和 `cancelOrder` 必须一致。顺序一旦反转就和下单路径成环，而**死锁只在并发下以 `40P01` 暴露，靠代码评审看不出来**。所以我有一条专门的集成测试反复制造 `create × cancel` 交叉（5 轮），断言不出现死锁。

### 3.4 短租约 + execution epoch 栅栏

**问题：** Agent 执行是几十秒到几分钟级的。如果用一个"执行期间持有租约"的方案，就需要周期性续租，而续租失败时**已经开始的工作无法撤销**——它可能正在等模型响应。

**方案：**

1. **短租约**：`claim` 领取时写 `lease_until = now + 30s`，**提交后立即归还数据库连接**。执行期间由心跳每 10 秒续租一次。
2. **`execution_epoch` 栅栏**：每次 `claim` 都让 epoch 加一，并且**所有写回都带 epoch 条件**：

```sql
WHERE run_id=? AND active_command_id=? AND execution_epoch=? AND lease_owner=?
```

旧 Worker 被接管后再写，`UPDATE` 的受影响行数就是 0，写不进去。

3. **心跳判定用命令期限，不用已运行时长**：`shouldRenewLease(deadlineAt, now) = deadlineAt.isAfter(now)`。`PLANNING` 通道允许 210 秒，因为慢模型响应加三级 Replan 必须能跑满这个期限。**用"已运行超过 90 秒就杀"这种硬阈值会误杀正常的长规划。**

**中断语义要分清：** `DependencyInterruptedException` 的语义是"被期限终止"，必须在分类时**早于 `Timeout` 判断**。否则期限届满会被误报成"外部服务超时"，排查方向直接跑偏。

**会被追问：** "租约到期但 Worker 还活着怎么办？"
答：两件事同时成立——心跳续租会失败（`LEASE_LOST`），而 epoch 栅栏保证它即使继续跑也写不进去。恢复由另一条路径承担：`recoverExpired` 把过期租约对应的命令翻回可重派发状态。**这里的顺序不能颠倒：必须先释放用户许可，再让命令可派发。** 反了的话，`recoverExpired` 把命令改成 `RETRY_WAIT` 且 `available_at = now()`，100ms 后就被捞起来，而此时 Redis 里的用户许可仍被上一任执行占着（TTL 240 秒），`tryAcquireUser` 失败 → 命令被塞回队首 → 下个周期再弹一次，**同一个用户就被自己的旧执行堵住最长 4 分钟**。

### 3.5 慢调用不拖垮数据库

这是压测/容量类问题的标准答案，核心只有一句：**网络等待期间不持有数据库连接。**

具体三处：

1. **租约**：`claim` 是短事务，提交即归还连接。agent DB 连接池只有 **12** 个——**按短事务吞吐配，不按 LLM 并发配**。如果租约覆盖整个执行过程，20 个规划线程就需要 20+ 个长连接，池子会被打爆。
2. **图执行**：`RunExecutionLock` 的实现**故意什么都不做**——跨实例串行化已经由短租约和 epoch 承担，绝不能再开一个覆盖整个 LangGraph / LLM / MCP 调用的数据库事务。
3. **Outbox**：三段式——短事务把事件标成 `CLAIMED` → **提交并归还连接** → 事务外发 HTTP → 用 `claimed_by` 条件更新成 `PUBLISHED` 或重新排队。**Webhook 卡住时不会握着 outbox 行锁和数据库连接。**

还有两处容易漏的：

- **依赖隔离**：DeepSeek / MCP Read / MCP Write / Embedding 四个依赖**各自独立线程池 + 超时 + 熔断**。MCP 读并发 32、写并发 16——**慢读不能占满写通道**，否则一次知识库检索抖动就会让下单全部卡住。
- **投递与回收分离调度**：投递是"跑完整个积压才返回"的循环，回收只是两条 `UPDATE`。**共用单线程会让回收被积压饿死。**

## 4. 追问链（真实面试的走法）

每条链都是"你说了 A → 他问 A 的边界 → 你答 → 他再深一层"。

### 链 1：从"幂等"走到"你到底证明了没有"

| # | 面试官 | 你 |
| --- | --- | --- |
| 1 | 幂等怎么做的？ | 三层：入口 `Idempotency-Key` + 唯一索引、领域 effect ledger、恢复按 `source_snapshot_id` 查重。 |
| 2 | 为什么需要第三层？ | 前两层都假设请求身份稳定。客户端每次重试换一个新幂等键的话前两层全失效，只有"来源快照唯一"能兜。 |

## 5. 高风险问题与翻车点

### 5.1 "RAG 的 0.65 是原来就有还是你写的？"

诚实回答：**是原有代码里的值，我发现它不可达。** 说清是"发现并修复"而不是"我一开始就写对了"——后者反而不可信，因为没人能一次把阈值写对。

### 5.2 "测试替身和生产实现一致吗？"

**这里我踩过真实的坑，可以主动讲。** `InMemoryCommerceEngine` 是测试替身，当初缺少生产里有的 `assertEffectUser` 校验，导致"越权取消"这条断言**在替身上恒绿**，而生产会抛 `EFFECT_USER_MISMATCH`。**替身一旦比生产宽松，它就是假绿的温床。** 修的时候要遍历全部语义对齐，不是补一个方法了事。

### 5.3 "集成测试里 `@Transactional` 生效吗？"

**这是集成测试最容易写成假绿的地方。** `@Transactional` 只对 Spring 容器创建的 bean 生效。在测试里手动 `new JdbcCommerceEngine(jdbc, json)` 得到的对象**根本没有事务**——`SELECT FOR UPDATE` 和 `pg_advisory_xact_lock` 全部退化成空操作，测试全绿但什么都没证明。

我的 IT 里所有引擎调用都用统一的 `inTransaction(...)` 包装（`TransactionTemplate`）。

### 5.4 "你怎么知道某个能力不存在？"

**这是一个方法论问题，我犯过。** 我曾经写过"项目没有配置 failsafe，集成测试只能手动跑"——**这是错的**。根 `pom.xml` 里既有 surefire 的 `<exclude>**/*IT.java</exclude>`，也有 `integration` profile 下的 failsafe。真相是：**"`mvn test` 不跑集成测试"是设计，不是缺失。**

教训：**写"某能力不存在"这类否定判断前，必须去查配置本身，不能因为跑 `mvn test` 时没看到 IT 就反推"没有配置"。否定性结论的举证责任更高**——它会把一份本可自动守护的保证，降级成需要人工记忆的口头约定。

### 5.5 "有没有只在你自己机器上通过的测试？"

**有，而且刚被 CI 抓出来。** `stopsExactlyAtTheDeadline` 断言"期限恰好等于当前时刻就停止续租"，测试里用 `acceptedAt.plus(PLANNING_DEADLINE)` **自己重算** `now`。但这个值写进 `timestamptz` 只保留**微秒**，而 Linux 的 `Instant.now()` 有**纳秒**精度，纳秒被舍入后重算的 `now` 可能比落库值早不到 1 微秒，判定就从 `STOP` 翻成 `RENEWED`。

**macOS 的 `Instant.now()` 本身就是微秒精度（实测 2000 次采样亚微秒位全为 0），所以这个红在开发机上永远不会出现。**

修法：`now` 取**库里读回来的那一列**。生产判定读的就是这一列，用持久化值当真值比测试侧重算更忠实，同时免疫精度问题。我还补了一条反向断言"早一纳秒必须续租"，把边界两侧都钉住。

**根因是证实的，不是推测的**：我在本地模拟纳秒时钟（`acceptedAt.plusNanos(700)`）复现出了与 CI **一字不差**的 `expected: <STOP> but was: <RENEWED>`。

## 6. 六个真实踩坑（这部分最能证明在做工程）

| # | 坑 | 本质 | 修法 |
| --- | --- | --- | --- |
| 1 | 测试替身比生产宽松 → 越权断言恒绿 | 替身与生产语义分叉 | 遍历对齐全部语义，不只补一个方法 |
| 2 | 手动 `new` 的引擎 `@Transactional` 不生效 → IT 全绿但没意义 | 容器的代理边界 | 统一 `TransactionTemplate` 包装 |
| 3 | RAG 阈值 `0.65` 不可达 → 接了线永远是死的且不报错 | **配置看起来正确、功能从未生效** | 金标集标定 + 打印相似度矩阵 + 字面量一致性断言 |
| 4 | 回补金额写死 `+1`，单点断言全绿 | 单点断言证明力弱于全局不变量 | 补守恒律断言 |
| 5 | CI 时钟精度假红（macOS 看不到） | 平台差异 + 断言依赖亚微秒精度 | `now` 取持久化值，边界两侧都断言 |
| 6 | 把"没看到 IT 执行"当成"没有 failsafe 配置" | **否定性结论的举证责任更高** | 查配置本身；已写进文档并更正 |

**第 3 条是最值得展开的一个**：它属于"配置看起来正确、功能从未生效"这一类缺陷——最典型的形态是**不报错的失效**。同类问题还有：连接池配好了但从没被并发打到、熔断器配好了但阈值永远不触发、索引建了但查询走的是另一个条件。**能识别这一类缺陷，比会修 bug 更值钱。**
